# Калькулятор распространения радиоволн

Веб-приложение для инженерной оценки радиотрасс «точка–точка» и «точка–подвижный объект»
на частотах **500–7000 МГц** с учётом рельефа, статистических моделей, параметров
оборудования и динамических объектов. Разработано по ТЗ v1.0.

## Архитектура (ТЗ 3.1)

Гибридная с абстракцией модели:

```
┌───────────────────────────── Next.js 16 (React + TypeScript, PWA) ─────────────┐
│  UI: карта Leaflet · ввод WGS84/СК-42 · упрощённо/подробно · графики Recharts │
│  Модели (интерфейс PropagationModel: calculate() + getCapabilities()):        │
│    • HttpPropagationModel → POST /api/calculate (FastAPI)                     │
│    • WasmPropagationModel  → Pyodide (Python в браузере)                      │
│    • LocalPropagationModel → TS FSPL + P.526 (fallback, всегда доступна)      │
└──────────────┬─────────────────────────────────────────┬───────────────────────┘
               │ /api (XTransformPort=8000 в песочнице)  │ IndexedDB
┌──────────────▼───────────────┐         ┌───────────────▼──────────────────────┐
│  FastAPI (Python, порт 8000) │         │  Локально в браузере:                │
│  P.2001-lite / py2001        │         │  • история расчётов (device_id)      │
│  карты ITU (.txt/.zip, 413)  │         │  • кэш SRTM .hgt, карт ITU (wasm)    │
│  clutter.geojson, история    │         │  • Service Worker (офлайн)           │
│  DEM-прокси (Copernicus GLO-30, AWS Terrain Tiles)                           │
└──────────────────────────────┘         └──────────────────────────────────────┘
```

Выбор бэкенда: `NEXT_PUBLIC_MODEL_BACKEND=http|wasm` при сборке (ТЗ 6.3) или в UI.

## Запуск

### Песочница (текущее окружение)
- Frontend: `bun run dev` (порт 3000, шлюз `?XTransformPort=8000` → сервис).
- Сервис: `cd mini-services/radio-service && uvicorn main:app --port 8000`.
- Переменные: `.env` → `NEXT_PUBLIC_MODEL_BACKEND=http`, `NEXT_PUBLIC_API_PORT=8000`.

### Локально (вне песочницы)
Шлюз `?XTransformPort=8000` существует только в песочнице; локально фронт
должен ходить на Python-сервис напрямую через `NEXT_PUBLIC_API_BASE`:

```bash
# 1. Python-сервис (порт 8000)
cd mini-services/radio-service
python -m venv .venv
.venv/Scripts/pip install -r requirements.txt   # Linux/macOS: .venv/bin/pip
.venv/Scripts/python -m uvicorn main:app --host 127.0.0.1 --port 8000

# 2. Frontend (порт 3000, из корня репозитория)
NEXT_PUBLIC_API_BASE=http://127.0.0.1:8000/api bun install && NEXT_PUBLIC_API_BASE=http://127.0.0.1:8000/api bun run dev
```

Без `NEXT_PUBLIC_API_BASE` запросы `/api/*` уходят в Next.js и HttpPropagationModel
молча переключается на локальный TS-fallback (FSPL + P.526) с предупреждением в UI.

### Гибридный режим http (ТЗ 6.1)
```bash
docker compose -f deploy/docker-compose.yml up -d --build
# тома: ./data/itu_maps, ./data/clutter, ./data/history
# обратный прокси: deploy/openresty.conf (/api → backend:8000, / → frontend:3000)
# HTTPS — в 1Panel (Let's Encrypt), client_max_body_size ≥ 1.1 ГБ
```

### Клиентский режим wasm (ТЗ 6.2)
```bash
docker compose -f deploy/docker-compose.wasm.yml up -d --build
# только frontend; карты ITU пользователь загружает в IndexedDB через UI
```

## Анализ качества линии (роадмап, этап 1)

Три функции «доверия к цифрам» — считаются клиентски поверх результата любого движка
(http/wasm/local), формулы продублированы и протестированы в python-сервисе
(`mini-services/radio-service/reports.py`, `p2001_lite.py`):

- **Availability-отчёт (ITU-R P.530-19)** — прогноз недоступности ч/год: многолучёвость
  §2.3.2 (p = p₀·10^(−FM/10), p₀ — фактор возникновения по климатической зоне и длине
  трассы) + дождь §2.4.1 (A₀.₀₁ по P.838 с path reduction factor d₀ = 35·e^(−0.015·R₀.₀₁),
  интерполяция A(p) = A₀.₀₁·0.12·p^(−(0.546+0.043·lg p))). Цели 99.5/99.9/99.99 % —
  требуемый запас (численное решение) vs фактический. R₀.₀₁ — из карт ITU P.837-6,
  ввода пользователя или оценки по зоне дождя (P.837-3). Карточка в результатах,
  строка «Прогноз недоступности (P.530)» в расходе бюджета, секция в JSON/CSV.
- **Clearance-аудит трассы** — просвет 0.6·F₁ при K = 4/3, 2/3, ∞ по профилю
  (рельеф + clutter); вердикты «0.6·F₁ выполнен / частичный просвет / перекрыта»,
  класс трассы «лёгкая/тяжёлая» (light = 0.6·F₁ и при 4/3, и при 2/3), доп.
  дифракционные потери подрефракции (K=2/3 относительно K=4/3). Блок в карточке
  «Профиль трассы» + бейдж класса на карте.
- **Шумовой порог P.372-17** — селектор «Шумовое окружение» в приёмнике
  (тихая сельская / сельская / жилая застройка / город): техногенный шум
  Fa = c − d·lg f (Table 1, фит валиден 0.3–250 МГц, в полосе 500–7000 МГц —
  экстраполяция с зажимом на 0 дБ), N = kTB + 10lg(f_rx + f_a − 1). По умолчанию
  «не учитывать» — бюджет не меняется; эффект даёт «Город / бизнес» на 500–610 МГц.

## Решения (ТЗ 9.3 — фиксируются в README)

1. **Анимация ≥ 24 FPS** — реализована упрощённая анимация траектории на карте с измерением
   фактического FPS в первые 1.5 с. В проверке на десктопе — 59 FPS (анимация включена);
   при < 24 FPS анимация автоматически отключается с сообщением и пользователю предлагаются
   интерактивные графики с tooltip (время, угол места, азимут, доплер, link margin).
2. **P.528** — не подключена: по ТЗ она добавляется только если сравнительные тесты на
   авиатрассах покажут улучшение > 5% относительно P.2001. В динамике реализован
   «авиационный» подход внутри P.2001-lite (приёмник на высоте полёта, LOS-геометрия).
   Точка интеграции: пакет `p528` (Python, MIT) в http-режиме.
3. **SXF — аддитивная интеграция**: конвертация выполняется офлайн-скриптом в
   clutter.geojson; контракты profile/dem/budget не изменялись, поэтому регрессионное
   тестирование контрактов не требуется (высоты подмешиваются в профиль отдельным слоем).
4. **WASM P.2001 через Pyodide** — Python-модуль `p2001_lite.py` (копия в `public/py/`,
   прекэшируется SW) выполняется в браузере. При недоступности Pyodide — fallback на
   локальную TS-модель FSPL + P.526 с предупреждением в UI (причина фиксируется в warnings).
5. **py2001** — в http-режиме сервис проверяет наличие пакета `py2001` и карт ITU
   (`/api/capabilities`, `/api/health`); при их отсутствии использует P.2001-lite,
   сообщая об этом в `engineUsed`. Точка расширения для полной реализации P.2001.
6. **Динамические объекты — прямолинейная траектория** с постоянной скоростью (по ТЗ 9.3),
   радиальная скорость — аналитически d(slant)/dt.
7. **История — по device_id, без авторизации**; при недоступности сервера — только IndexedDB.
8. **СК-42** — усреднённые элементы трансформирования WGS84→СК-42 (точность плановых
   координат ~2–5 м по территории РФ; проекция Гаусса–Крюгера сверена с pyproj ±0.2 м).
   Для геодезической точности суб-метра подключите локальные параметры трансформирования
   в `src/lib/radio/coordinates.ts`.
9. **P.676** — упрощённая модель (ТЗ 4.7 допускает «упрощённую модель или с профилями
   P.835»), калибрована по справочным кривым; применима до ~57 ГГц (рабочий диапазон
   приложения 0.5–7 ГГц).
10. **Link margin** — по формуле ТЗ `SNR − Eb/N0_req`; дополнительно отображается
    классическое Eb/N₀ (с учётом B/R) для сверки с методиками.

## Тестирование (ТЗ 7)

```bash
# Юнит-тесты ядра TypeScript (55 тестов):
bun test tests/

# Юнит-тесты формул Python (25 тестов): P.2001-lite, P.838, P.676, бюджет, доплер
cd mini-services/radio-service
pip install -r requirements.txt pytest
python3 -m pytest tests/ -q
```

Покрыто: формулы P.525/P.526/P.838/P.676/P.833; бюджет линии (EIRP, SNR, link margin);
доплеровский сдвиг; координаты; парсер .hgt; валидация clutter.

Интеграционные испытания (P.2001 http/wasm vs эталон MATLAB/SEAMCAT на 5–10 трассах,
регрессия FSPL+P.526 ≤ 0.1 дБ, Lighthouse PWA ≥ 90) выполняются на стенде приёмки
и требуют эталонных реализаций вне этой поставки.

# Калькулятор распространения радиоволн

Веб-приложение для инженерной оценки радиотрасс «точка–точка» и «точка–подвижный объект»
на частотах **500–7000 МГц** с учётом рельефа, статистических моделей, параметров
оборудования и динамических объектов. Разработано по ТЗ v1.0.

## Архитектура (ТЗ 3.1)

Гибридная с абстракцией модели:

```
┌───────────────────────────── Next.js 16 (React + TypeScript, PWA) ─────────────┐
│  UI: карта Leaflet · ввод WGS84/СК-42 · упрощённо/подробно · графики Recharts │
│  Модели (интерфейс PropagationModel: calculate() + getCapabilities()):        │
│    • HttpPropagationModel → POST /api/calculate (FastAPI)                     │
│    • WasmPropagationModel  → Pyodide (Python в браузере)                      │
│    • LocalPropagationModel → TS FSPL + P.526 (fallback, всегда доступна)      │
└──────────────┬─────────────────────────────────────────┬───────────────────────┘
               │ /api (XTransformPort=8000 в песочнице)  │ IndexedDB
┌──────────────▼───────────────┐         ┌───────────────▼──────────────────────┐
│  FastAPI (Python, порт 8000) │         │  Локально в браузере:                │
│  P.2001-lite / py2001        │         │  • история расчётов (device_id)      │
│  карты ITU (.txt/.zip, 413)  │         │  • кэш SRTM .hgt, карт ITU (wasm)    │
│  clutter.geojson, история    │         │  • Service Worker (офлайн)           │
│  DEM-прокси (Copernicus GLO-30, AWS Terrain Tiles)                           │
└──────────────────────────────┘         └──────────────────────────────────────┘
```

Выбор бэкенда: `NEXT_PUBLIC_MODEL_BACKEND=http|wasm` при сборке (ТЗ 6.3) или в UI.

## Запуск

### Песочница (текущее окружение)
- Frontend: `bun run dev` (порт 3000, шлюз `?XTransformPort=8000` → сервис).
- Сервис: `cd mini-services/radio-service && uvicorn main:app --port 8000`.
- Переменные: `.env` → `NEXT_PUBLIC_MODEL_BACKEND=http`, `NEXT_PUBLIC_API_PORT=8000`.

### Локально (вне песочницы)
Шлюз `?XTransformPort=8000` существует только в песочнице; локально фронт
должен ходить на Python-сервис напрямую через `NEXT_PUBLIC_API_BASE`:

```bash
# 1. Python-сервис (порт 8000)
cd mini-services/radio-service
python -m venv .venv
.venv/Scripts/pip install -r requirements.txt   # Linux/macOS: .venv/bin/pip
.venv/Scripts/python -m uvicorn main:app --host 127.0.0.1 --port 8000

# 2. Frontend (порт 3000, из корня репозитория)
NEXT_PUBLIC_API_BASE=http://127.0.0.1:8000/api bun install && NEXT_PUBLIC_API_BASE=http://127.0.0.1:8000/api bun run dev
```

Без `NEXT_PUBLIC_API_BASE` запросы `/api/*` уходят в Next.js и HttpPropagationModel
молча переключается на локальный TS-fallback (FSPL + P.526) с предупреждением в UI.

### Гибридный режим http (ТЗ 6.1)
```bash
docker compose -f deploy/docker-compose.yml up -d --build
# тома: ./data/itu_maps, ./data/clutter, ./data/history
# обратный прокси: deploy/openresty.conf (/api → backend:8000, / → frontend:3000)
# HTTPS — в 1Panel (Let's Encrypt), client_max_body_size ≥ 1.1 ГБ
```

### Клиентский режим wasm (ТЗ 6.2)
```bash
docker compose -f deploy/docker-compose.wasm.yml up -d --build
# только frontend; карты ITU пользователь загружает в IndexedDB через UI
```

## Анализ качества линии (роадмап, этап 1)

Три функции «доверия к цифрам» — считаются клиентски поверх результата любого движка
(http/wasm/local), формулы продублированы и протестированы в python-сервисе
(`mini-services/radio-service/reports.py`, `p2001_lite.py`):

- **Availability-отчёт (ITU-R P.530-19)** — прогноз недоступности ч/год: многолучёвость
  §2.3.2 (p = p₀·10^(−FM/10), p₀ — фактор возникновения по климатической зоне и длине
  трассы) + дождь §2.4.1 (A₀.₀₁ по P.838 с path reduction factor d₀ = 35·e^(−0.015·R₀.₀₁),
  интерполяция A(p) = A₀.₀₁·0.12·p^(−(0.546+0.043·lg p))). Цели 99.5/99.9/99.99 % —
  требуемый запас (численное решение) vs фактический. R₀.₀₁ — из карт ITU P.837-6,
  ввода пользователя или оценки по зоне дождя (P.837-3). Карточка в результатах,
  строка «Прогноз недоступности (P.530)» в расходе бюджета, секция в JSON/CSV.
- **Clearance-аудит трассы** — просвет 0.6·F₁ при K = 4/3, 2/3, ∞ по профилю
  (рельеф + clutter); вердикты «0.6·F₁ выполнен / частичный просвет / перекрыта»,
  класс трассы «лёгкая/тяжёлая» (light = 0.6·F₁ и при 4/3, и при 2/3), доп.
  дифракционные потери подрефракции (K=2/3 относительно K=4/3). Блок в карточке
  «Профиль трассы» + бейдж класса на карте.
- **Шумовой порог P.372-17** — селектор «Шумовое окружение» в приёмнике
  (тихая сельская / сельская / жилая застройка / город): техногенный шум
  Fa = c − d·lg f (Table 1, фит валиден 0.3–250 МГц, в полосе 500–7000 МГц —
  экстраполяция с зажимом на 0 дБ), N = kTB + 10lg(f_rx + f_a − 1). По умолчанию
  «не учитывать» — бюджет не меняется; эффект даёт «Город / бизнес» на 500–610 МГц.
- **Сравнение методов дифракции (P.526)** — при затенении в результатах
  раскрывается таблица: Буллингтон (§4.5.2) / Дейгаут (§4.4) / Эпштейн–Петерсон
  (§4.5.1) и текущая оценка max(Д, Б), разброс методов в дБ. Методы сходятся —
  оценке можно верить; разброс >5–10 дБ — неопределённость высока (несколько
  сопоставимых препятствий), запас лучше брать по худшей оценке. Медиана не меняется.

## Модель Longley-Rice ITM (роадмап 2.1)

Третья модель распространения ('itm') — независимая оценка NLOS по неровному
рельефу. Реализация: **вендоренный порт ITM v1.2.2** (FORTRAN→Python от
[AB3AP/Mike Markowski](https://github.com/ab3ap/itm); оригинальный код NTIA/ITS —
public domain, работа правительства США, см. [NTIA/itm-longley-rice](https://github.com/NTIA/itm-longley-rice))
в `mini-services/radio-service/itm_port.py` + адаптер `itm_model.py`.

Конвенции: climate = 5 (континентальный умеренный — категории ITM 1–7 не
маппятся на зоны дождя ITU), поверхностная рефракция N0 = 301 N-ед.
(DN_Median из карт — градиент ΔN, не N0), epsR/sigma из ввода (P.527).
Итоговые потери = FSPL по длине профиля + избыточное затухание ITM
(Eq 5.1/5.2 TN101); квантили времени zT = Φ⁻¹(p/100) — кривая убывает с
ростом p, как в ITU. Выбор модели — в блоке «Модель распространения»;
при выбранном ITM в результатах появляется карточка «Сравнение моделей:
ITM vs P.2001» с перекрёстным расчётом и Δ.

**Разрыв движков (задокументирован)**: ITM реализован только в python-сервисе
(http-модель). TS/wasm-реализации нет: при недоступности сервиса (или в
wasm-режиме) выполняется локальный расчёт P.2001-lite с явным предупреждением
(ранее неизвестные модели молча уходили в FSPL+P.526 — исправлено).

## Динамика UAV (роадмап 2.2)

Расчёт динамики — клиентская функция (формулы потерь те же, что в p2001lite и
reports.py, покрытые тестами в обоих движках): для каждого сэмпла строится
профиль рельефа между станцией и текущей позицией объекта, потери — медианная
цепочка FSPL + P.526 (дифракция, buildings) + газы; растительность не
применяется (полёт над лесом). Наведение антенн — по текущему углу места
с номинальным углом из параметров. Тайлы рельефа вдоль траектории подкачиваются
с сервера автоматически (`requiredTilesForPolyline`). Скорости 0–300 км/ч.

## Поиск оптимальной позиции точки A

Чекбокс «Поиск позиции» у точки A (ввод): при включении появляется поле
«Радиус поиска, м» (ввод вручную, не более 5000). При расчёте приложение
перебирает 61 кандидатную позицию (кольца 0.25R/0.5R/0.75R/R — 8/12/16/24
азимута + исходная точка) с **полной оценкой линии**: все параметры связи и
приёмо-передатчиков — из выполненного расчёта, меняется только позиция A
(профиль трассы перестраивается по рельефу, clutter учитывается). Результат —
сворачиваемый блок в результатах: в свёрнутом состоянии «найдено N оптимальных
точек» (лучше исходной по запасу), в развёрнутом — таблица кандидатов
с координатами СК-42 Гаусс–Крюгер (X и Y по 7 цифр, Y с номером зоны), запасом,
P_rx, потерями и удалением от исходной позиции. У каждого кандидата —
пиктограмма круговой диаграммы: при наведении показывается предпросмотр
покрытия, рассчитанного от позиции кандидата (радиус «трасса кандидата +
10 км», кэшируется); кнопка «Применить» переносит точку A в позицию кандидата
и пересчитывает. Критерий оптимальности — link margin прямой линии; позиции
оцениваются локальной моделью (те же формулы, что выбранная) для скорости
перебора. В основной круговой диаграмме покрытия — подложка из рельефа,
без слоя карты.

## UX-пакет (роадмап, этап UX — по референсу antenna.2tg.dev)

- **Share-ссылка** (UX.1): кнопка «Поделиться» рядом с «Рассчитать» копирует URL, в котором
  в URL-hash закодированы все входные параметры расчёта (точки A/Б, частоты обеих станций с
  режимами и диапазонами, поляризация, высоты, k-фактор, климатическая зона, атмосфера,
  оборудование, модель) + автозапуск расчёта (`run=1`). Открывший ссылку получает применённый
  ввод и выполненный расчёт; рельеф подтягивается автоматически (подкачка тайлов с сервера).
  Карты ITU, clutter и файл маршрута не сериализуются. Формат — hash, а не query: роутер
  Next.js не затрагивается; декод только на клиенте (`src/lib/radio/share.ts`, zod-валидация,
  невалидное поле игнорируется).
- **Пользовательские пресеты оборудования** (UX.2): пресеты создаёт сам пользователь — в
  карточке станции кнопка «Сохранить пресет как…» (модальное окно с вводом имени) сохраняет
  снимок антенны и приёмопередатчика станции (высота антенны не входит). Хранение —
  localStorage (`radio-presets`), применение к любой станции из обеих карточек. Импорт/экспорт
  JSON-файла — вкладка «Карты и настройки», секция «Пресеты оборудования»: экспорт всего списка;
  импорт в двух режимах — «добавить к существующим» (дубликаты по id/имени+станции пропускаются)
  или «переписать существующие» с красным предупреждением о безвозвратной перезаписи.
- **Режимы преград кругового покрытия** (UX.3): селектор «Преграды на покрытии» в диаграмме —
  «текущая модель (FSPL+P.526+clutter)» (по умолчанию, как в основном расчёте), «только FSPL —
  оптимистичная» (без рельефа и препятствий), «геометрия LOS — худший случай» (рельеф/
  препятствия выше прямой обрывают зону), «строго по Френелю (0.6·F1)» (уверенный приём —
  полный F1). Легенда и подписи карточек адаптируются под режим, у каждого режима — честное
  описание границ применимости. В `computeFsplP526` добавлен аддитивный opts
  `{skipDiffraction}` (все существующие вызовы не меняются).
- **Перетаскивание маркеров A/Б** (UX.4): маркеры на карте — персистентные инстансы, переносятся
  мышью, `dragend` переносит координаты в форму (без автопересчёта — расчёт по кнопке, как
  принято в проекте).
- **Полноэкранный режим карты** (UX.5): кнопка «Во весь экран» (CSS fixed-контейнер,
  `map.invalidateSize()`, Escape закрывает; Fullscreen API сознательно не используется —
  надёжнее в PWA).
- **Mesh-заготовка** (UX.6): `src/lib/radio/mesh.ts` — только типы (звено/цепочка) и точка
  расширения `evaluateMeshChain` (бросает исключение); пункт роадмапа 2.4 «сеть линий»
  ЗАМОРОЖЕН, расчёта и UI нет (решение пользователя 2026-11-13).

## Интерференция C/I (роадмап 2.3)

Расчёт помехи от второго источника: путь помехи — **ITU-R P.452-18** (вендоренный
порт [Py452](https://github.com/eeveetza/Py452) в python-сервисе, функционально идентичен
эталонной реализации ITU-R SG3; лицензия допускает вендоринг с атрибуцией — см.
`mini-services/radio-service/p452_port/LICENSE`), вердикт — на клиенте.

- **Ввод**: чекбокс «Источник помехи (C/I, P.452)» в карточке «Трасса» — координаты
  (WGS 84/СК-42, как у точек A/Б; на карте — режим клика «Клик → помеха», маркер C
  перетаскивается), высота, мощность, усиление, частота помехи, радиоклиматическая зона
  P.452 (1 прибрежная суша / 2 суша / 3 море), защитное отношение C/I_min (по умолчанию
  = Eb/N0 приёмника — «интерференция как шум»).
- **Жертвы**: Rx прямой линии (точка Б) и Rx обратной линии (точка A) — по два пути
  P.452; разнос антенн жертвы учитывается через ширину луча (угол между лучом на свой
  передатчик и направлением на помеху), Gt/Gr в вызове P.452 = 0.
- **Отчёт «Помехи (C/I)»**: уровни I, I/N, C/I vs C/I_min, C/(N+I), деградация шума
  Δ = 10lg(1 + I/N) и класс влияния (< 0.5 дБ — не влияет … ≥ 3 дБ — сильное) —
  для медианы p = 50 % и коротковременной помехи p = 1 %.
- **Карты ITU не распространяются**: скачайте N050.TXT/DN50.TXT с сайта ITU
  (`scripts/download_p452_maps.ps1`) и соберите `data/p452/P452.npz`
  (`scripts/build_p452_npz.py`). Без npz сервис отвечает «P.452 недоступен», клиент
  честно уходит в **фоллбек P.2001-lite** (медиана 50 %, без p = 1 %) с предупреждением
  в карточке.
- Допущения: помеха ко-канальная (полное спектральное перекрытие) и складывается с
  шумом как шум; помеха не входит в историю/экспорты (только карточка результатов).

## Покрытие на карте (роадмап 2.5)

Уровни сигнала из круговой диаграммы (`computeCoverage`) рисуются
**геопривязанным канва-оверлеем** на карте MapPanel — визуальный аргумент
«что видно с точки A».

- **Данные**: `computeCoverage` дополнительно сохраняет уровни по контрольной
  сетке 72 радиала × 60 дальностей (`CoverageResult.levels`, ~17 КБ) — те же
  точки, что и раньше, без дополнительных расчётов. Режимы преград
  (UX.3: model / fspl / geometry / fresnel) действуют и на карте.
- **Рендер**: чистый модуль `src/lib/radio/map-coverage.ts` — offscreen-канва
  512×512, пиксель → (дальность, азимут) → билинейная интерполяция уровня →
  цвет зоны; `canvas.toDataURL` → `L.imageOverlay` с bounds по локальной
  плоской проекции (lat ± R/111320, lon ± R/(111320·cos(φ))).
- **Зоны** (согласованы с tri-color статусами): ≥ 10 дБ — уверенный приём
  (тёмно-зелёный), 0–10 — связь (зелёный), −10–0 — на грани (янтарный),
  < −10 — нет связи (красный полупрозрачный). Геометрические режимы:
  заливка до границы радиала (fresnel: полный просвет — темнее).
- **Управление**: слой включается автоматически после расчёта; кнопка
  «Покрытие на карте» в тулбаре карты скрывает/возвращает; слайдер —
  непрозрачность; бейдж «покрыто N % · макс X км» — статистика диска.

## Решения (ТЗ 9.3 — фиксируются в README)

1. **Анимация ≥ 24 FPS** — реализована упрощённая анимация траектории на карте с измерением
   фактического FPS в первые 1.5 с. В проверке на десктопе — 59 FPS (анимация включена);
   при < 24 FPS анимация автоматически отключается с сообщением и пользователю предлагаются
   интерактивные графики с tooltip (время, угол места, азимут, доплер, link margin).
2. **P.528** — не подключена: по ТЗ она добавляется только если сравнительные тесты на
   авиатрассах покажут улучшение > 5% относительно P.2001. В динамике реализован
   «авиационный» подход внутри P.2001-lite (приёмник на высоте полёта, LOS-геометрия).
   Точка интеграции: пакет `p528` (Python, MIT) в http-режиме.
3. **SXF — аддитивная интеграция**: конвертация выполняется офлайн-скриптом в
   clutter.geojson; контракты profile/dem/budget не изменялись, поэтому регрессионное
   тестирование контрактов не требуется (высоты подмешиваются в профиль отдельным слоем).
4. **WASM P.2001 через Pyodide** — Python-модуль `p2001_lite.py` (копия в `public/py/`,
   прекэшируется SW) выполняется в браузере. При недоступности Pyodide — fallback на
   локальную TS-модель FSPL + P.526 с предупреждением в UI (причина фиксируется в warnings).
5. **py2001** — в http-режиме сервис проверяет наличие пакета `py2001` и карт ITU
   (`/api/capabilities`, `/api/health`); при их отсутствии использует P.2001-lite,
   сообщая об этом в `engineUsed`. Точка расширения для полной реализации P.2001.
6. **Динамические объекты — прямолинейная траектория** с постоянной скоростью (по ТЗ 9.3),
   радиальная скорость — аналитически d(slant)/dt.
7. **История — по device_id, без авторизации**; при недоступности сервера — только IndexedDB.
8. **СК-42** — усреднённые элементы трансформирования WGS84→СК-42 (точность плановых
   координат ~2–5 м по территории РФ; проекция Гаусса–Крюгера сверена с pyproj ±0.2 м).
   Для геодезической точности суб-метра подключите локальные параметры трансформирования
   в `src/lib/radio/coordinates.ts`.
9. **P.676** — упрощённая модель (ТЗ 4.7 допускает «упрощённую модель или с профилями
   P.835»), калибрована по справочным кривым; применима до ~57 ГГц (рабочий диапазон
   приложения 0.5–7 ГГц).
10. **Link margin** — по формуле ТЗ `SNR − Eb/N0_req`; дополнительно отображается
    классическое Eb/N₀ (с учётом B/R) для сверки с методиками.
